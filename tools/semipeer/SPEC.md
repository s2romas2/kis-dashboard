# 반도체 peer 쌍 선정 — 작업 지침

## 목적
투자자가 "A기업이 peer보다 싸다"를 판단하려면 **peer를 누구로 잡느냐**가 가장 중요하다. 잘못 잡으면 밸류 평가가 통째로 틀린다.
그래서 같은 세부분야에 있다는 이유만으로 peer로 묶지 않고, 쌍(pair)마다 5개 기준으로 점수를 매기고 **근거를 원문 인용으로** 남긴다.
이 결과는 대시보드의 "peer 상대밸류" 화면에 그대로 노출되고, A·B등급 쌍만 저밸류 판정에 쓰인다. C등급은 "참고용"으로만 표시된다.
등급은 점수로 자동 계산하므로 직접 적지 않는다. **점수를 후하게 주지 말 것** — 애매하면 낮은 점수, 자료에 없으면 null.

## 입력
`bundles/<batch>.json` 하나. 안에 들어 있는 것:
- `fields`: 세부분야별 1~3위(`rank`: why·gap·refs 인용문), `dissent`, `industry`
- `companies`: 기업별 `semimap`(제품·용도·강점), `detail`(sub·spec·diff·kpi·refs), `scale`(시총·매출·영업이익률 — 체급 감 잡는 용도)
- `segment_summaries`: 일부 분야의 산업 요약

## 5개 기준 (각 0 / 1 / 2 / null)
| id | 기준 | 2점 | 1점 | 0점 |
|---|---|---|---|---|
| prod | 제품 동일성 | 같은 제품을 같은 용도로 팔아 고객이 서로 대체 가능한 직접 경쟁 | 같은 제품군이지만 방식·세대·용도가 달라 부분 경쟁 | 다른 제품(같은 공정 단계에 있을 뿐) |
| cust | 고객 중복 | 주요 고객사가 실명으로 겹침 | 같은 고객군(예: 메모리 3사)이지만 주력 고객이 다름 | 고객군 자체가 다름 |
| mix | 매출 비중(순수도) | 양사 모두 이 제품이 전사 매출의 과반 | 한쪽만 주력이고 다른 쪽은 일부 사업 | 양쪽 다 부수 사업이거나, 한쪽이 대기업·지주사라 전사 멀티플이 이 사업을 반영하지 못함 |
| model | 사업모델·단계 | 판매 구조와 사업 단계가 같음(예: 둘 다 장비사 직납, 둘 다 양산 매출) | 일부 다름 | 다름(양산 vs 개발·진입 단계, 캡티브 vs 외판, 장비 vs 소모품 등) |
| driver | 실적 드라이버 | 실적을 움직이는 전방 변수가 같음(같은 고객의 같은 투자·가동률) | 일부 겹침 | 다름(예: 모바일 AP vs 데이터센터) |

- **null = 자료에서 확인 못 함.** 추측으로 채우지 말 것. 이때 `why`에는 "미확인 — (무엇을 확인해야 하는지)"를 적는다.
- cust·mix가 null이라 등급이 깎이는 쌍 중 prod가 2인 쌍에 한해서만, 웹 검색(사업보고서·증권사 리포트·전문매체)으로 보완해도 된다. 쌍당 검색 2회 이내. 못 찾으면 null 유지.

## 무엇을 쌍으로 만들 것인가
1. 같은 `field`의 rank에 함께 있는 기업끼리는 **전부** 평가한다(결과가 C여도 적는다 — 사람들이 흔히 비교하는 조합이므로 "비교하면 안 되는 이유"가 중요하다).
2. field가 달라도 제품·고객이 실제로 겹치면 쌍을 추가한다(예: 포고핀 소켓 vs 러버 소켓).
3. rank에 없는 기업(`detail.fields`가 비었거나 detail이 없는 기업)도 bundle 안에서 가장 가까운 상대를 찾아 쌍을 만든다. 정말 없으면 `nopeer`에 이유와 함께 적는다.
4. bundle의 모든 기업은 pair 1개 이상 또는 `nopeer`에 반드시 등장해야 한다.
5. 그룹(`groups`)은 화면에 묶어 보여 주는 단위다. 보통 field 하나가 그룹 하나지만, 성격이 같은 field는 합쳐도 되고 cross-field 그룹을 새로 만들어도 된다. 한 쌍은 한 그룹에만 넣는다. 한 기업은 여러 그룹에 들어가도 된다.

## 출력 — `out/<batch>.json`
```json
{
 "groups": [
  {
   "id": "testsocket",
   "name": "테스트 소켓(포고핀·러버)",
   "seg": "테스트부품",
   "basis": "이 묶음을 peer 후보로 보는 이유. 자료에 있는 사실만, 2~3문장.",
   "caution": "이 묶음에서 밸류를 비교할 때 조심할 구조적 차이. 1~2문장.",
   "members": ["058470", "095340"],
   "pairs": [
    {
     "a": "058470", "b": "095340",
     "score": {"prod": 1, "cust": 0, "mix": 2, "model": 1, "driver": 0},
     "why": {
      "prod": "둘 다 IC 테스트 소켓이지만 리노공업은 포고핀(R&D용), ISC는 러버(양산용)로 방식과 쓰임이 다름",
      "cust": "리노공업은 모바일 AP 고객, ISC는 데이터센터 칩 고객 중심으로 고객군이 갈림",
      "mix": "양사 모두 테스트 소켓이 주력 사업",
      "model": "둘 다 소켓 외판이나 리노공업은 R&D 단계 소켓, ISC는 양산 소켓 비중이 높음",
      "driver": "리노공업은 스마트폰 AP 신제품, ISC는 데이터센터 투자에 실적이 연동"
     },
     "ev": [

     ],
     "verdict": "같은 소켓 업종이지만 전방 시장이 달라 PER 차이를 곧바로 저평가로 읽으면 안 됨",

    }
   ],
   "nopeer": [
    {"c": "000000", "why": "국내 상장사 중 같은 제품을 파는 곳이 없음 — 이유 한두 문장"}
   ]

 ],
 "companies": [
  {"c": "058470", "pure": "high", "main": "IC 테스트 소켓·포고핀이 매출 대부분", "ev": {"c": "058470", "q": "IC테스트소켓 66% / 리노핀 23% / 의료기기 11%"}}

 "global_peers": [
  {"c": "058470", "names": ["WinWay"], "ev": {"c": "058470", "q": "WinWay 2026E P/E 114배 vs 리노 46배"}}

```

### 필드 규칙
- `score`: 5개 키 모두 필수. 값은 0, 1, 2, null만.
- `why`: 5개 키 모두 필수. 각 15~140자. 쉬운 말로. 전문용어는 처음 나올 때 짧게 풀어 쓴다.
- `ev`: 쌍당 2개 이상. 두 형태만 허용.
  - bundle 인용: `{"c": "<종목코드 6자리>", "q": "<bundle에 있는 문장을 한 글자도 바꾸지 않고 그대로 복사>"}` — q는 12자 이상, 그 기업의 semimap/detail 또는 그 기업이 속한 field 안에 실제로 있어야 한다. 검증기가 대조한다.
  - 웹 인용: `{"u": "https://...", "t": "문서 제목", "b": "발행처", "q": "<페이지에서 직접 본 문장 그대로>"}` — 실제로 열어서 본 문장만. 기억으로 쓰지 말 것.
- `verdict`: 한 문장. 이 쌍의 멀티플을 직접 비교해도 되는지에 대한 결론.
- `premium`: 어느 쪽이 구조적으로 프리미엄(또는 할인)을 받는 게 타당한지와 이유. 없으면 빈 문자열.
- `companies[].pure`: 그 기업 전사 매출에서 반도체 해당 제품이 차지하는 정도. `high`(과반) / `mid`(주요 사업 중 하나) / `low`(일부 — 대기업·지주사·타 산업 주력) / `unknown`. bundle의 모든 기업에 대해 작성. `ev`는 있으면 붙이고 없으면 생략.
- `global_peers`: bundle에 해외 경쟁사가 실명으로 언급된 경우만. 없으면 빈 배열.
- **PER·PBR·목표주가 같은 밸류 숫자는 why/verdict/premium에 쓰지 말 것**(화면에서 실시간 값으로 따로 계산한다). 영업이익률, 매출 비중, 고객사명, 점유율 같은 사업 사실은 써도 된다.
- 비상장·코드가 6자리 숫자가 아닌 기업은 쌍에 넣지 않는다(`nopeer`·`companies`에서도 제외).

## 검증
작성 후 `python3 validate.py <batch>` 를 실행해 **오류 0이 될 때까지** 고친다. 인용문 불일치는 문장을 지어내지 말고 bundle에서 다시 복사한다.

## 보고
끝나면 5줄 이내로: 그룹 수, 쌍 수, 점수 합계 8 이상 쌍 수, nopeer 수, 판단이 특히 어려웠던 쌍 1~2개와 이유.
# 추가 지침 — 소부장 맵 밖 기업(웹 조사 배치)

SPEC.md의 기준·출력 형식·검증을 그대로 따르되, 아래가 다르다.

- bundle의 `new: true` 기업은 대시보드에 기존 자료가 없다. **웹 조사로 근거를 확보**해야 한다.
- 근거 우선순위: ① DART 사업보고서·분기보고서(주요 제품 매출 비중, 주요 고객, 사업의 내용) ② 증권사·한국IR협의회 기업리포트 원문 ③ 전문매체(디일렉·전자신문·ZDNet Korea·TrendForce 등) ④ 회사 IR 자료. 블로그·커뮤니티·종목 집계 사이트는 근거로 쓰지 않는다.
- 웹 인용 형식: `{"u": "https://...", "t": "문서 제목", "b": "발행처", "d": "YYYY-MM-DD(알면)", "q": "페이지에서 직접 본 문장 그대로"}`.
  **실제로 열어 본 페이지의 문장만** 인용한다. 검색 결과 요약이나 기억으로 인용문을 만들지 말 것. 나중에 URL을 다시 열어 인용문을 대조한다 — 대조에서 틀리면 그 쌍 전체를 버린다.
- 확인하지 못한 기준은 null로 두고 why에 "미확인 — …"을 적는다. 억지로 채우지 않는다.
- 국내 상장사 중 직접 peer가 없으면(예: 순수 파운드리) `nopeer`에 적고, 해외 peer가 자료에 실명으로 나오면 `global_peers`에 남긴다. 해외 기업은 쌍에 넣지 않는다.
- 삼성전자처럼 여러 사업을 가진 기업은 `companies[].pure`를 정확히 판단하고(반도체 매출·이익 비중 근거 인용), 전사 멀티플 비교의 한계를 `caution`과 `verdict`에 분명히 적는다.
- `new: false` 기업끼리의 쌍은 만들지 않는다(다른 배치가 담당). new 기업 ↔ new 기업, new 기업 ↔ 참고 기업 쌍만 만든다. `companies`·coverage 검증은 new 기업만 채우면 된다(참고 기업은 pair에 쓰였을 때만 등장).
